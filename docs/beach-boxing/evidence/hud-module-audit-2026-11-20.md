## Runtime progression rules recovered from shipped Wasm

- Number formatting is `n <= 999 ? n.ToString() : ((float)n / 1000f).ToString("0.00") + "k"`. Thus 4240 displays `4.24k`; one million displays `1000.00k`. No million suffix or explicit culture provider. Source `WorkingOutManager-FormatNumber.wat:25`, function 50059.
- Saved `PrestigeLVL` defaults to 1. Its ten stages use `maxStatScores` thresholds. For each independent muscle, raw fraction is `(strength - thresholds[level-1]) / (thresholds[level] - thresholds[level-1])`. Image fill clamps through Unity; full overlay activates when raw fraction >= 1. Source `WorkingOutManager-LoadStats.wat:1085`, function 12034; fill/full bindings at line 1453.
- The manual `LVL UP` entry appears once all four muscle fractions reach 1, while level <= 9. Actual `LvlUp` increments PrestigeLVL, hides the holder and calls LoadStats; scores are retained. Source `WorkingOutManager-LoadStats.wat:1505` and `WorkingOutManager-LvlUp.wat:25`, function 50056. The native entry is GO 129 under holders 339/220, with Join Room BTN 2, duplicate `LVL UP` text, glow and `!` badge. That entry opens a menu; it is distinct from trainer upgrade buttons.
- Displayed rank is `titles[CurOpponent / 5]`, integer division, independent of strength and prestige. Displayed `LVL` is PrestigeLVL. Source `WorkingOutManager-LoadStats.wat:548` and `:578`.
- Whole-player uniform scale by level is `[1,1.15,1.3,1.45,1.6,1.7,1.8,1.9,2,2.1]`. Native camera target local Y is `[0,1,2,2.5,3,3.2,3.4,3.6,3.8,4]`. Source `WorkingOutManager-LoadStats.wat:68`; these values must be translated through the recreation's established world scale.
- Per-group body parts interpolate from their `startProduct` local pose toward their original local pose with clamped fraction, using Vector3.Lerp position/scale and Quaternion.Lerp rotation. Muscle.Awake captures the original pose. Source `Muscle-Awake.wat:1` function 49801; `MuscleManager-UpdateTorsoMuscles.wat:78` function 9395; the other groups are functions 9394/9393/9392. The initial 0.1 assignments in LoadStats are overwritten by actual fractions; there is no final minimum 0.1.
- Base strength gain for level 1..10 is `[11,13,15,20,24,28,33,38,43,48]`. Per repetition, gain is `(int)(base * (1f + selectedMuscleModifier/100f))`, truncating toward zero. Update completes at workoutProgress >= 0.99. CompleteWorkout adds the gain without a strength cap, updates stats/morph, resets repetition state and updates recommended weight. Source `WorkingOutManager-Update.wat:1091`, level switch at `:1110`, modifier multiplication at `:1231`, truncation at `:1339`; `WorkingOutManager-CompleteWorkout.wat:64`. Current fixed 7 gain differs from the shipped level-1 base 11.
- Recommended weight for nonnegative strength is `Clamp(RoundToEven((strength*0.0196667f+5f)/5f)*5,5,300)`. LinearReturn uses the same first round with maximum 300; CalculateRecommendedWeight redundantly rounds to a multiple of five again and enforces minimum 5. These govern weight/difficulty, not the base strength-gain array. Sources `WorkingOutManager-LinearReturn.wat:1` (50058), `WorkingOutManager-CalculateRecommendedWeight.wat:1` (5882).

## Integration boundaries

Extend the existing preplaced `BeachHud` and serialized scene bindings for native row fills, full overlays, top-right buttons, badges and panels. Keep original sprites and Lilita font/material profiles. Bind growth/name/rank through the existing stage/BoxerView owner rather than recreating the player model. Reuse `ProgressStore`/`LocalStore` for persistent game state, with an explicit compatible version migration. A narrow rewarded-ad adapter can bridge native rewards to QG SDK and an Editor outcome implementation; the raw SDK alone is not a completed reward flow.

`LocalStore` uses unqualified `PlayerPrefs`. The project's global `Assets/VIVO-GAME-SDK/Runtime/PlayerPrefs.cs` routes WebGL reads/writes to `QG.Storage*Sync`; desktop reads/writes use `UnityEngine.PlayerPrefs`. QG writes are synchronous and its wrapper Save() is empty on WebGL. Preserve this platform storage boundary.

Stop conditions for claims of completeness: verify native number formatting, bar/level/rank/body-growth formulas, menu/badge tutorial gating, trainer purchase/equip/reward behavior, daily claim/date logic and desktop/mobile interaction rules. Then implement and validate those behaviors. Current core fight/training loop and restored art do not establish those peripheral conditions.
