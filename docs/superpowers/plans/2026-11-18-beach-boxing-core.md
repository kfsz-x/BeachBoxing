# Beach Boxing 核心玩法开发计划

> 执行时使用 `executing-plans`，按任务顺序更新复选框和验收记录。已通过的证据及剩余差异见文末进度。

**目标：**在现有 Unity 工程中交付可打 vivo 小游戏包的核心循环：进入训练区、训练成长、选对手、打擂台、结算、重赛或解锁下一位，退出后保留进度。

**架构：**保留框架的 `Init → Game → MainPanel` 启动路径，通过 `MainPanel.gameplayScene` 接独立玩法场景。训练、拳赛和结算共用一个场景，由流程控制器切换区域、镜头和 UI。触屏和键鼠转成同一份输入；战斗规则、训练奖励和对手配置独立于 UI。

**技术栈：**Unity `2021.3.14f1c1`、C#、现有 uGUI、Unity 物理、现有 vivo SDK 和 WebGL。Unity MCP 用于场景接线和编辑器检查；REA、Il2CppDumper 用于原包取证。

**玩法规格：**本文件的「范围与基准」及 M0 输出的参考记录。原包公式和参数以证据记录为准。

## 范围与基准

- **对照版本：**`D:/Desktop/Beach_Boxing_Simulator_100%原版包体/` 内的离线 Unity `2022.3.34f1` WebGL 包。已确认启动及 IL2CPP 元数据 v31；尚未确认完整战斗规则。
- **首版范围：**移动、交互、核心训练、成长、选对手、出拳、格挡、体力、敌方 AI、胜负、重赛、基础解锁和存档。M2、M3 先用一项训练和一位对手贯通，再补 M0 核实且直接参与主循环的项目。首版至少有两位对手，用于验收解锁和难度差异。
- **对齐重点：**玩家输入响应、动作节奏、命中判定、对手行为、训练增量、结算奖励、解锁条件。按最新要求，交付的角色、场地、器材、UI、特效、动画和音效复用原包资源。占位仅供本地联调；交付前核对原版资源引用。广告、每日奖励、拆箱、药水和装饰功能暂缓；若某项阻断主循环，先确认最小替代规则。
- **手机优先：**计划暂按仓库 vivo `manifest.json` 的竖屏默认值，适配安全区，支持移动与攻击或格挡组合触控；保留键鼠调试。若原包实测表明横竖屏差异会改变拳赛视野或按键布局，先确认方向，再定 HUD。
- **实现选择：**用独立玩法场景接框架，便于保留示例入口及独立迭代；训练和擂台先在同一场景切换，减少 WebGL 重载和对象重复初始化。若 M0 证实原包跨场景加载本身影响体验，再决定是否拆场景。
- **约束：**本阶段保留编辑器版本、旧输入后端、现有 SDK 和启动顺序。玩法资源先使用场景引用和本地资源；如需动态资源，复用 `CoreRoot.Resources` 与本地 Addressables。正式 vivo 包由用户打包并在手机测试；开发侧先交付构建前检查、WebGL 冒烟记录和真机清单。

## 任务与验收

### M0：测出原包玩法基准

- [ ] 用隔离的浏览器配置从新档录一遍：进入训练、一次成功训练、选人、拳赛胜负、重赛、解锁。记录视口、帧率、输入时刻和前后属性。补同一对手的无格挡、持续格挡、空拳和体力不足样本；关键分支重复验证，区分随机差异。
- [ ] 记录触屏布局、相机方向、移动和交互方式；桌面模拟触摸与真机观察分开标注。确认训练项目、首批对手、UI 提示和存档恢复行为。
- [ ] 用 REA 关联 `BoxingController`、`EnemyManager`、`WorkingOutManager` 等符号与观察。将 WASM 和元数据复制到工程外，使用官方 Il2CppDumper 发行版试跑并记下版本、命令和结果。若无法映射，继续用可读的资源配置和逐帧实测；二进制工具不是继续开发的门槛。
- [ ] 交付 `reference-baseline.md`：每条记录含场景、初始状态、输入、观察、证明材料、可信度和验收方式。标记「实测」「静态推断」「待验证」；无法恢复的参数独立配置并记为近似。整数属性、奖励及解锁比较精确值；时间比较采用 M0 测得的帧率、可辨误差和采样区间，先记阈值再验收。若关键判定无法区分，先提出复测方案；只有差异会改变范围时才询问用户。

**过关：**能按记录复跑首轮核心循环；首版范围、关键数值、已知未知项及验收阈值有据可查。

### M1：接入框架和输入，提前找出 WebGL 风险

- [ ] 新建玩法程序集和场景。用 Unity MCP 查看当前场景和编译状态；添加场景与入口绑定，保留 `Init → Game`、设置及音量入口。启动进入训练区，返回现有菜单。
- [ ] `BeachInput.ReadFrame(): InputFrame` 每帧输出移动向量、攻击按下/松开/按住和格挡状态；`TouchControl` 按触点 ID 认领摇杆及按钮。只在当前状态启用可用操作；状态退出、失焦、触摸取消、应用暂停时清掉移动及按住状态。`BeachMotor` 驱动角色；键鼠仅接入同一输入层。
- [ ] 先用当前 WebGL 目标构建并启动占位场景，检查启动场景顺序、uGUI 射线、资源引用及触屏。同步书面记录 vivo SDK 转换入口、配置来源和预期输出；无需用户此时打正式包。

**过关：**从 `Init` 冷启动可进出玩法场景；输入取消后不中断下一次操作。双指组合、拖出按钮、暂停恢复各验证一次；记录 WebGL 构建及加载结果。

### M2：训练和成长闭环

- [ ] `BeachGameFlow` 管理 `Training`、`OpponentSelect`、`Fight`、`Result`。`TrainingStation` 用 M0 确认的交互和完成条件申报一次训练结果。先做一项：靠近、开始、结束或取消、显示成长；离开或中途退出按参考规则处理。
- [ ] `ProgressStore.Load(): PlayerProgress`、`ProgressStore.Save(PlayerProgress)` 通过 `CoreRoot.Storage` 的独立键读写带版本号的进度。记录 M0 核实的属性与解锁字段；完成且生效后保存，暂停时刷盘。缺档初始化；坏档在保留原记录的前提下恢复可用状态。
- [ ] 用 HUD 显示实际变化；为 M0 已确认的其他核心训练配置同一奖励通路。训练奖励在完成一次时只入账一次，与拳赛结算分开。

**过关：**同档重复一轮训练增量一致；取消与重复结束回调符合规则；重启恢复已确认的进度；训练后的属性在 M3 影响拳赛。

### M3：拳赛、敌方 AI 和结算

- [ ] `FightController` 开局时从 `PlayerProgress` 和 `OpponentProfile` 取得本场属性快照；`FightRules` 管体力消耗/恢复、格挡与受击判定、伤害和终局。用 M0 的动作阶段驱动命中窗口；同一出拳对同一目标至多结算一次。与画面帧率解耦，优先让动画、判定和反馈保持同一时间轴。
- [ ] `OpponentBrain` 按 M0 样本实现距离、血量和体力相关的进退、出拳、格挡和恢复，把决策参数集中在 `OpponentProfile`。先完成第一位对手，再接第二位及首版确认范围内的核心对手。验收时允许固定种子复现，正常游戏保留实测到的随机差异。
- [ ] `BeachGameFlow` 负责选人、开战、结算、回训练及重赛；一次拳赛只接收一次终局和领奖。`BeachHud` 呈现有证据的战斗状态、结束动作和解锁提示。重赛清空临时状态，保存成长和已解锁进度。

**过关：**固定输入可复跑命中、空拳、格挡、体力不足、胜、负和重赛；多碰撞回调不重复伤害或领奖；首胜解锁、输后不误解锁，重启可重进已解锁对手。

### M4：原包对照与体验收敛

- [ ] 将原包资源先导出到工程外。记录模型、贴图、材质、动画、音效、UI 和特效的来源及依赖；从导出品中选取核心玩法实际使用的资源，保留引用关系。将它们接入原工程玩法场景和预制体；脚本绑定用新玩法程序集，原包工程设置和平台 SDK 不覆盖现有配置。
- [ ] 在 Unity 2021.3 对每类导入资源检查缺失引用、材质显示、动画绑定和 UI 切图；对 2022.3 序列化或 Shader 差异做兼容处理。不能恢复的资源列出原文件、失败原因和影响，确认后才决定如何交付。

- [ ] 用同一条件比较原包与复刻：起点和对手、属性快照、输入顺序和时间；对比移速、镜头、开始与命中时间、体力、伤害、结算及解锁。保存原包与复刻的对照证据。按「阻断流程 → 判定错误 → 节奏偏差 → 反馈差异」处理。
- [ ] 用 Unity Test Framework 的 EditMode 覆盖数值、存档和奖励幂等；PlayMode 覆盖 `Init → 训练 → 选人 → 胜负/重赛 → 重启`。用 Unity MCP 检查实际场景连线和运行日志；在 WebGL 中另跑低帧率、重复重赛、暂停恢复和触屏手势。
- [ ] 对照记录标记结果为通过、可接受近似或待确认。主循环阻塞、错发奖励、丢进度、输入卡死均须修复；不能确认的细节报告差异和证据，不写成已实现 1:1。

**过关：**主循环可重复，测试及人工样本有结果；关键指标达到 M0 记录的阈值，或明确写出差异并交用户复核。

### M5：vivo 打包交接与真机回测

- [ ] 在当前 Unity 版本检查 `Init` 为首场景、玩法场景已启用、使用 WebGL Support、资源可本地加载，以及 vivo 模板实际采用的方向。先验证标准 WebGL 构建日志与浏览器冷启动；vivo 路径记为 `VIVO小游戏 / 转换小游戏`。构建成功以输出与错误日志为准。
- [ ] 写 `vivo-handoff.md`：场景顺序、构建配置、vivo 转换入口、输出核对、已知局限和回报模板。记录测试包对应工程版本；如需要 vivo 项目 ID 或签名，由用户在打包端填写。
- [ ] 用户打包后，真机依次做：冷启动、双指移动加攻击/格挡、完成训练、胜负各一次、重赛、切后台返回、重开读档。记录机型、系统/小游戏运行环境、包版本、方向、复现步骤、录屏和日志；记录首屏时间、帧率波动和重复三场后的稳定性。
- [ ] 根据真机回报修正可复现问题，并按原复现步骤复验。若用户尚未回传结果，状态标记为「已交付待真机验收」。

**过关：**开发交付包含可打包工程、构建记录和真机清单；真机通过由用户反馈或实际设备记录确认。

## 优先复查的边界情况

| 情况 | 预期 | 验收任务 |
| --- | --- | --- |
| 移动和格挡同时按住，切后台 | 回到前台时旧触点不再持续输入，新触摸有效。 | M1、M5 |
| 训练中途退出，完成回调重入 | 依参考规则记账；同一完成事件至多发一次。 | M2 |
| 拳套在命中窗口内多次进入碰撞体 | 同一拳对同一对手只结算一次。 | M3 |
| 结束按钮连点后重开 | 一份结算，临时战斗状态归零，永久进度保留。 | M3、M4 |
| vivo 断网冷开或重开 | 基础训练和拳赛可进，成功保存的进度可恢复。 | M5 |

## 推进方式

按 `M0 → M1 → M2 → M3 → M4 → M5` 执行。每阶段记录改动、实际测到的结果、剩余差异和下一步。首个可玩交付点是 M3；M4 验收后进入 M5 打包交接。M0 完成后按实测覆盖范围估算工期。方向、主循环删减或关键规则缺证且无法复测时，再向用户确认。

### 核心玩法第二轮

1. 补原版肌肉图标、计量条、胜负界面和受击遮罩，沿用现有屏幕安全区结构。
2. 按 WASM 恢复训练进度、出拳成本与格挡反馈。保留标注为近似的判定和镜头。
3. 检查资源引用和编辑器导入，把双指和数值回归交给 vivo 真机验收。

本轮改动已写入当前工程。训练在新档每次加 11，出拳费用改按手臂属性，举盾恢复按背部属性调整；战斗与结算界面接入新增原版切图。拳套判定、镜头和 AI 未完成逐帧对照。vivo 由用户打包和验收。
